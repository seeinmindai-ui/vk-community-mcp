# Обслуживание

Тесты выполняются без реальных токенов и без вызовов VK. Зелёные тесты не означают работоспособности всех операций с конкретным токеном VK.

## Состояние

```bash
systemctl is-active vk-community
systemctl is-enabled vk-community
curl --fail https://mcp.shmasiki.pro/vk/health
```

Без авторизации `/vk/mcp` должен возвращать 401 с OAuth metadata challenge. Health подтверждает процесс, а не доступность VK.

## Обновление

1. Изменить код в ветке, проверить лицензии новых компонентов и отсутствие секретов.
2. Выполнить тесты и проверку публикации. Зафиксировать версии зависимостей.
3. Обновить `main`, затем передвинуть `production` на проверенный commit без force push.
4. Серверный таймер получает публичную production-ветку. SHA и пути проверяются; активный релиз не перезаписывается.
5. Новый релиз строится в отдельном каталоге, тестируется, ссылка `current` переключается атомарно. Health проверяется; при ошибке ссылка возвращается на прежний релиз.

Это автоматизация исполнения уже проверенных изменений. Она не умеет оценивать безопасность будущего кода; доступ к production равнозначен праву обновлять службу. Не публикуйте серверные или GitHub-токены ради деплоя. Для публичного репозитория чтение возможно без токена. Новые зависимости должны быть отдельно проверены.

## Откат и отключение

Остановить только `vk-community`, вернуть ссылку `/opt/mcp/vk/current` на предыдущий релиз, запустить службу и проверить health/401. Для полного отключения также остановить таймер обновления и отключить маршруты VK в Caddy, предварительно проверив и сохранив действующий Caddyfile. Не возвращайте старый Caddyfile целиком поверх чужих изменений.

База и ключ остаются на месте. Откат кода не является откатом публикаций/сообщений в VK. Не выполняйте очистку состояния и отзыв токенов без отдельного решения владельца.

## Браузерные формы OAuth

Для `/vk/login` и `/vk/approve` используется `Referrer-Policy: same-origin`. Глобальный `no-referrer` может превращать Origin обычной POST-формы в `null` и конфликтовать со строгой проверкой Origin. Для остальных ответов остаётся no-referrer. Проверки точного Origin, одноразового CSRF, cookies и пароля не ослабляются. [Поведение браузера](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Referrer-Policy#effect_on_the_origin_header).

Login-форма разрешает в CSP только свой источник и origin точного redirect URI, уже проверенного SDK по регистрации клиента. Это позволяет Chrome пройти303 к loopback Codex или callback облачного клиента, сохраняя ограничение form-action. Временная диагностика отказов содержит только фиксированный код причины и время, без логинов, паролей, URL, cookies и токенов. Значение `auth-diagnostic/latest` доступно только через серверное администрирование, не анонимный endpoint.

### Регистрация ChatGPT и области доступа

ChatGPT может опустить scope при DCR, затем запросить vk:read/vk:write при авторизации. Регистрация без scope разрешает клиенту запрашивать оба реализованных scope; явно зарегистрированный read-only клиент остаётся ограниченным чтением. Регистрация сама по себе не создаёт access/refresh/code: доступ выдаётся после входа owner и подтверждения отображённых прав. Ранее сохранённый DCR-клиент ChatGPT с vk:read требует отдельного исправления метаданных либо повторной регистрации; изменение default_scopes не меняет сохранённые регистрации. Не удалять клиентские секреты/активные подключения для исправления. [Официальная документация](https://developers.openai.com/plugins/build/auth) описывает повторное использование зарегистрированного клиента ChatGPT.
